# DO-178C 软件保证计划

状态：v2.1.0 起执行；本文件是项目内部软件保证基线。

## 1. 适用性与声明边界

本项目从 v2.1.0 开始采用 DO-178C 的需求驱动开发、双向追踪、验证、配置管理和问题报告方法。DO-178C 本身不是 Rust 编码规范，也不能仅凭代码、测试或 CI 获得认证。

本项目不是已批准的机载系统，当前没有系统安全评估、失效条件分类、审定计划、审定机构认可的工具鉴定或指定软件等级。因此：

- 不声明“DO-178C 认证”“符合某个 DAL”或可用于安全关键飞行控制；
- 在系统安全评估确定软件等级前，执行不依赖等级的严格目标，并保存证据；
- 如果未来进入机载审定，必须由合格人员建立 PSAC，并根据指定等级补齐独立性、结构覆盖、目标覆盖和工具鉴定证据；
- Gemini、第三方本地模型及其训练数据属于外部组件，不能因为本项目采用该流程而自动视为已认证软件。

## 2. 生命周期数据

受配置管理的生命周期数据包括：

1. 高层和低层软件需求：`docs/assurance/SOFTWARE_REQUIREMENTS.md`；
2. 需求—设计—代码—验证追踪：`docs/assurance/TRACEABILITY.md`；
3. Rust/Slint 编码规则：`docs/assurance/CODING_STANDARD.md`；
4. 架构和版本验收门：`docs/PC_RUST_SLINT_ROADMAP.md`；
5. 源代码、测试、锁文件、CI 定义和发布脚本；
6. 评审记录、GitHub PR、CI 结果、真机测试记录和问题报告。

所有版本均从受控 Git 提交和锁定依赖构建。需求、代码或测试发生变更时，必须在同一 PR 更新追踪关系。

## 3. 开发过程

执行顺序为：

1. 分配唯一需求 ID；
2. 记录安全、资源、时序和异常行为；
3. 写正常、边界和鲁棒性测试；
4. 实现最小变更；
5. 执行格式、静态分析、测试和平台构建；
6. 独立复核需求、实现和证据；
7. 在目标设备执行无法由 CI 代替的验证；
8. 关闭问题报告后才进入版本验收。

派生需求必须明确标记来源，并反馈到系统/产品需求。未经需求支持的代码必须删除、隔离或补充获批需求，避免不可追踪代码。

## 4. 验证策略

- **评审**：需求应正确、一致、可验证、无歧义；代码应符合标准并追踪到需求。
- **分析**：并发、队列上限、数值范围、错误隔离、敏感数据生命周期和最坏执行时间必须分析。
- **测试**：覆盖正常范围、边界、无效输入、资源耗尽、取消、重复事件和故障恢复。
- **结构覆盖**：CI 收集覆盖率是后续任务；达到 100% 语句/分支并不替代需求覆盖。若未来等级要求 MC/DC，必须使用适用工具并处理不可达代码。
- **目标设备**：权限、音频时钟、设备热插拔、系统休眠、窗口行为和端到端时延必须在 Windows/macOS 真机验证。

测试代码中的 `expect` 只用于明确测试前置条件；生产路径禁止依赖 panic、未检查索引或无界资源作为错误处理。

## 5. 配置管理与问题报告

- `Cargo.lock`、`package-lock.json` 和 Gradle 版本属于配置项；
- 版本只能通过 `scripts/set-version.mjs` 更新，并由一致性测试验证；
- 失败 CI、真机异常、需求偏差和安全问题必须形成可追踪问题；
- 修复必须包含复现、根因、影响分析、回归测试和关闭证据；
- 发布产物必须对应唯一提交、依赖锁、构建环境和校验值。

## 6. 完成标准

一个版本只有在需求已实现、双向追踪无缺口、验证通过、问题关闭、目标设备证据齐全且路线图验收门满足后才可推进版本号。CI 通过不等同于软件等级认定、审定批准或真机验证。
